# RFD: The research update takes its model from the one model card (Sonnet 5.5)

**Date**: 2026-10-29
**Status**: Implemented (committed; WatchTower pushes)
**Author**: WatchTower (Claude Opus 5.5) under Pouria's grant G-1

---

## Question

Pouria: "Everywhere … they all get their models from ONE model card, which must always be up to date … Don't break
anything." And: switch the weekly Google Scholar job from Opus to Sonnet.

## Plan and result

- The card is pr-ra's `backend/app/agents/models.py`, exported to `model-card.json` at pr-ra's root. pr-ra is checked
  out on the VPS at `/home/pouria/projects/pr-ra`, so the cron reads `/home/pouria/projects/pr-ra/model-card.json`,
  purpose `research_update` (`claude-sonnet-5-5`).
- `utils/research-update.config.json` `model` is now `claude-sonnet-5-5` too, and is the fallback when the card is
  missing, unreadable or lacks the purpose. The job never fails over the card.
- `resolve_model` runs once at config load (so `--dry-run`, the cooldown path and the logs work as before) and again
  right after `git pull --rebase`: before, the config was read before the pull, so a pushed change took effect a week
  later. The run log, `STATUS.md` and `history.jsonl` record the model and its source.
- Everything else in the script is unchanged (alerts, retries, cooldown, deploy verification).

## Verification

- `bash -n utils/update-research-cron.sh`.
- The resolver, extracted and run on the Mac: real card → `claude-sonnet-5-5` (card); missing, broken (`{bad`) and
  purpose-less cards → the config's value, labelled as such.
- On the VPS: `~/.local/bin/claude -p --model claude-sonnet-5-5 "Reply with the single word ok"` → `ok` (Claude Code
  accepts the id). `model-card.json` is not on the VPS yet (pr-ra's deploy brings it); until then the config's
  identical value is used. The cron script itself was not run.
